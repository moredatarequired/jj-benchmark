# The jj suite: prompts and grading

Every task's prompt, and what its verifier actually checks. **14 built and shipping** — 14 task directories in the tree, so that is the whole suite — plus **9 proposed** (design stage, plus one unassigned slot) and **7 cut**. Generated by `docs/build_suite_review.py`, which writes this file and `docs/suite_review.html` in the same run; prompts and test counts are read from `tasks/` at build time, not stored.

## How to read this

**Scoring.** A verifier is a set of pytest assertions. Any test that passes on the untouched image with no agent is **floored** — measured, not declared, by `scripts/vacuity_floor.py` — and is excluded from both sides of the fraction, so the reward is *(scored tests passed) / (scored tests)*. A floored test still has to pass: if pytest exits non-zero for any reason the reward is capped strictly below 1.0, so a failing floored guard caps a correct solve without otherwise penalising it. A no-agent run scores 0 on every task by construction — the only tests it passes are the floored ones, so its numerator is empty.

**Anchored.** Before the agent runs, the harness measures the untouched image and records the change ids the bootstrap gave each commit, the per-workspace working-copy keys and the handover operation id. A verifier is **anchored** when its assertions are phrased in those recorded ids rather than in descriptions, positions or bookmarks — which is what stops a repository rebuilt from `root()` collecting full marks. *With exemptions* means the task ships an `anchor_exemptions.json` naming the specific commits the asked-for work is allowed to remove. In cold CI there is no anchor file and each check falls back to what it asserted before, saying out loud that no identity claim was made.

**The proposed nine.** Nothing in the second section exists. No fixture, no verifier, no run, no measurement — so there is no test count, no floor, no anchor decision and no measured weakness for any of them. Their *graded* sentences describe what a verifier would assert.

## Shipping now — 14 built

The prompt shown is the file the agent is handed, `tasks/<name>/instruction.md`, read at build time; the grading is what `tests/test_final_state.py` asserts. All fourteen were rewritten from specifications into requests in `4c2a6de0`.

### abandon_commits

```text
abandon the commits experiment and draft point at, keeping the experiment bookmark but not the draft one, then describe the working copy "cleanup complete"
```

Four assertions on repository state. a.txt and d.txt are on disk and b.txt and c.txt are not, and the anchored handover working copy must track exactly those two files, so the abandons really took their files with them. `experiment` must resolve to the change id the bootstrap gave `commit A`, `draft` must no longer resolve at all, and the bootstrap's `commit C` must be invisible everywhere. Commits are named by anchored change id and by the anchor's per-workspace working-copy key, never by position — except that the description check also requires `@` to still BE the handover change.

`4 tests, 0 floored · anchored, with exemptions · separates models`

**Known hole.** That last `@` pin is incidental to the task: a correct solve that finishes with a fresh `jj new` on top loses a quarter of the reward.

### edit_commit_message

```text
"Add file B" should say "Add second file" instead, and I want a new commit on top of the working copy adding d.txt with "d" in it, described "Add file D"
```

The renamed commit is the bootstrap's own 'Add file B', found by anchored change id — `jj describe` preserves change ids, which is why a rename is checkable this way and a description is not — and must now contain 'Add second file'. The new commit is the agent's, so it has no anchored id and is anchored by relation instead: `@`'s parents must be exactly the anchored 'Add file C' change before its description and d.txt's contents are read. The docstring records that the parent claim is what killed a measured `jj new -r 'root()'` rebuild that had scored 1.0.

`4 tests, 1 floored · anchored · separates models`

**Known hole.** `@` must literally be the new 'Add file D' commit, so a correct solve that finishes with an extra `jj new` fails two of the three scored tests.

### rebase_branch

```text
rebase feature-branch onto main, resolving the conflict in the commit that has it: both lines, main's first
```

The rebase is graded as topology rather than as a count: `main` must be an ancestor of `feature-branch`, `main..feature-branch` must be exactly two commits forming a linear chain planted directly on main, and — when the anchor is present — those three must be the bootstrap's own commits by change id. The resolution is read with `jj file show data.txt` at the anchored head and compared line-wise (not byte-wise, so a missing trailing newline does not fail a correct answer) against ['Line from main', 'Line from feature']. Conflict-freedom is the floored test and comes from the `conflict` template keyword rather than from `jj resolve --list`'s prose.

`3 tests, 1 floored · anchored, with exemptions · separates models`

**Known hole.** The identity half of the topology test sits behind `if all(wanted.values())`, so with no anchor file it silently degrades to bookmarks-and-ancestry; and the conflict check is floored, so it earns nothing.

### restore_interactive

```text
the "remove legacy module" commit deleted settings.toml along with the module — put it back in that commit, changing nothing else
```

Six scored assertions, every one about a commit's tree or its own diff, byte-compared against the bootstrap's literal file contents. 'remove legacy module' must carry settings.toml at the original bytes and must no longer list it among the paths it changes while still changing exactly legacy.py and main.py; 'Initial commit' and 'add logging' must be untouched; the handover working copy must still change only notes.txt; and settings.toml must be back on disk. Named commits resolve by anchored change id and the working copy by the anchor's per-workspace key; the one positional element is deliberately relaxed to `@`-or-an-ancestor, which replaced an equality that had been failing correct solves that ran `jj new`.

`7 tests, 1 floored · anchored · separates models`

### split_commit_interactive

```text
split "Add feature A and feature B" into "Add feature A" with feature_a.py and then "Add feature B" with feature_b.py
```

The two halves are located from the bootstrap's own commit rather than by position: the anchored change is resolved, and whether the split gave its id to the newer or the older half is worked out from its parentage. Each half must resolve to exactly one commit and the anchored commit must be one of the two; the older must be described exactly 'Add feature A' with feature_a.py and not feature_b.py in its `jj diff -s`, the newer the mirror image. Both scored tests re-run that resolution, so a fabrication cannot collect half the reward, and the old `@`-position test is gone — it scored a textbook `jj edit` + `jj split -i` solve 0.5.

`2 tests, 0 floored · anchored, with exemptions · separates models`

**Known hole.** Only which filenames each half touches is graded, never the file contents, and `jj diff -s` is substring-matched — so a split that moves the right paths with the wrong bytes inside them still passes.

### squash_range

```text
merge the two fix commits into their parent (leave the current commit alone)
```

The three bootstrap survivors must still be visible and any other visible commit must render `empty` — a scratch commit is free, a commit still carrying content is not. The two fix changes must be gone by change id rather than by text (a squash folds their descriptions into the target, so a text search would flag a correct solve), structure.txt at the target must be exactly 'logic fixed', and parents are compared as change ids. The anti-fabrication test is an `--at-op` replay: the operation at which the fixes stopped being visible must also be the one at which their content arrived in the target, which fails hand-edit-then-`jj abandon` and cannot fail an honest route however many operations it took. Three of the eight tests pass on the untouched image, so five are scored, and that floor of 3 is the measured value. An earlier note here said the opposite; it was wrong. The 0-of-8 re-measurement in af369f13 was itself the corrupt one: it ran with a stale `tests/bootstrap_anchor.json` in the tree, which names change ids from an earlier build of the image, so the session-scoped fixture in `tests/conftest.py` raises and every test errors during setup — and "nothing passed" then gets written down as the floor. `ea80c334` restored the 3, and `scripts/vacuity_floor.py` now refuses to record a run that was zeroed that way rather than by the verifier.

`8 tests, 3 floored · anchored, with exemptions · separates models`

**Known hole.** The op-log replay authenticates the history against itself, so it is only the anchor that makes it an integrity check; and the op-count test that made this the sharpest separator in the 795-trial baseline was deleted for grading method rather than outcome, so two sequential squashes are now believed to score 1.0.

### template_customize_log_output

```text
add a template alias called log_custom that prints each commit's short change id, then " | ", then the first line of its description, one commit per line
```

Neither test grades a commit; the task carries no anchored claim of its own. `jj config get template-aliases.log_custom` must exit 0 and its value — after a real newline is normalised back to the two characters of an escape, so hand-written and `jj config set` forms compare equal — must name `change_id.short()`, `description.first_line()`, the ' | ' separator and a newline. The real assertion is the second: `jj log -r all() --no-graph -T log_custom` must render byte-identically to the verifier rendering the reference template over the same revisions, which is indifferent to quoting and to which config layer the alias lives in. That tolerance was written to fix a measured grader artifact: identical correct behaviour scored 1.0 hand-edited and 0.5 through `jj config set`.

`2 tests, 0 floored · not anchored · separates models`

**Known hole.** Nothing anchors the graded object, and on jj 0.44 a template runtime error renders `<Error: …>` inline at exit 0 — both sides of the byte comparison would render it identically, so the render test can pass on garbage until an explicit `<Error:` rejection is added.

### track_untracked_file

```text
app.log is ignored but I need it tracked, commit as "Track log file", don't touch the ignore rules
```

Everything is asserted about one commit: the change the bootstrap's working copy was sitting on, resolved through the anchor's reserved per-workspace key because its handover description was empty. That commit must list app.log in `jj file list` and its description must contain 'Track log file'. The floored third test byte-compares .gitignore against the bootstrap's exact contents both on disk and in that commit's tree. Nothing is positional — the previous version graded `@-`, which scored a correct `jj describe` finish 0 and a fabricated commit at `@-` a full 1.0.

`3 tests, 1 floored · anchored · separates models`

**Known hole.** The byte-exact .gitignore check that catches the `!app.log` cheat is the floored one, so that cheat still passes both scored tests and is only capped below 1.0 rather than zeroed.

### workspace_update_stale

```text
this workspace is stale — bring it up to date, then change config.json's status to "active" and commit that as "Activate config"
```

All three assertions additionally require the commit they inspect to be, or to descend from, the change this workspace's working copy was sitting on at handover — which is where the other workspace's work landed, and which the docstring records as what killed a measured fabricate-from-`root()` solve that had scored 1.0. `jj st` must exit 0 in the project (a stale working copy exits 1 on the pinned jj); config.json must parse with status 'active' and the other workspace's `new` field preserved, both on disk and in the commit at `@-`; and that commit's description must contain 'Activate config'.

`3 tests, 0 floored · anchored · separates models`

**Known hole.** The graded commit is `@-` by position, so a correct solve that finishes by describing the updated working copy in place fails two of the three scored tests. A redundant stderr grep for the word 'stale' also sits behind the exit-code check that already discriminates.

### absorb_changes

```text
push the feature_a.py and feature_b.py fixes in my working copy down into whichever commit last touched each file, so the working copy ends up empty
```

Graded as per-file placement, which is what distinguishes absorb from a wholesale squash. The anchored 'Initial commit' must touch feature_a.py in its own diff with the fix content there, and `{target}..@ & files(...)` must be empty so no later commit is still modifying that path; feature_b.py is the same test against the anchored 'Add feature A'. The third test requires `@` to be or to descend from that commit, to render `empty` and to have no changed paths — anchored by relation because the per-file `jj squash --into` route empties the handover `@` and jj abandons an emptied squash source.

`3 tests, 0 floored · anchored, with exemptions · provisional, held for coverage`

**Known hole.** The content check is a substring of the fix marker, so hand-placing the right line into the right ancestor passes without `jj absorb` ever running — correct under R3, but it means the task cannot distinguish absorb from a careful manual squash.

### undo_mistaken_rebase

```text
rebase B onto base, then put the repo back exactly the way it was before that
```

The operation log is replayed with `jj --at-op`, asking at each operation where the bootstrap's `B` change was sitting, as change ids. One scored test requires that at some recorded operation `B`'s only parent was the anchored `base`; the other requires that plus `B` sitting on `A` at the current operation with the `conflict` keyword false. The conjunction is deliberate: this task's correct end state IS its bootstrap state, so all four pure end-state assertions are in the vacuity floor and earn nothing. No route is named, so undo, op undo, op revert and op restore all qualify — the previous English-matching version mis-scored a throwaway rebase that never touched `B` at 1.0.

`6 tests, 4 floored · anchored · provisional, held for coverage`

**Known hole.** Only two scored tests, so a single grader artifact halves the task; and the replay cannot tell a deliberately staged rebase-and-revert from a genuine mistake — only the anchor rules that out.

### operation_recovery

```text
Commit 3, Commit 4 and Commit 5 were a mistake — put the repo back to how it was right after I made Commit 2
```

The recovered state is asserted commit by commit: file3/4/5.txt off disk and out of the tree of the anchored change the bootstrap went on to describe 'Commit 3', which must track exactly file1.txt and file2.txt; nothing described Commit 3, 4 or 5 visible, and the anchored Commit 4 and Commit 5 changes not resolving at all. Then `@` must BE that anchored 'Commit 3' change, render empty, be undescribed, and sit on the anchored 'Commit 2' — which is what separates going back to the earlier state from editing history forward into a similar-looking shape. Finally exactly four commits may be visible, and the three anchored changes must be among them.

`8 tests, 3 floored · anchored, with exemptions · provisional, held for coverage`

**Known hole.** `@` must be exactly the recovered change, so a correct recovery that ends standing somewhere else loses a fifth of the reward; and the commit-id equality that would catch a rebuild-then-`op restore` is floored, so it earns nothing.

### git_fetch_remote

```text
main has moved on origin — rebase feature onto the new main and push feature back up
```

Both assertions are made in the bare remote with git plumbing, against a commit id computed from the working repository at verification time: the rebase preserves the change id and rewrites the commit id, so the expected value cannot be stored anywhere. The bootstrap's 'Feature commit' change is resolved by anchored change id, and `git rev-parse refs/heads/feature` in the remote must equal what it resolves to now. The second test adds that the remote has a `main`, that `feature` is not the same commit as it, and that main is an ancestor of feature — which together kill the measured `git branch feature main` cheat that scored 1.0 without running jj at all.

`2 tests, 0 floored · anchored · provisional, held for coverage`

**Known hole.** The two scored tests overlap heavily — both assert the same equality — so the reward is close to pass/fail, and nothing asserts that a fetch ever happened.

### workspace_add

```text
set up a second workspace for this repo at /home/user/myproject-workspace2
```

The load-bearing claim, re-run in all three tests, is that the new directory is backed by the project's own repository: the change id the anchor recorded for the project's handover working copy must resolve from inside it, which a separately-created repository cannot do whatever it is named. Around that: the directory exists and `jj workspace root` there prints it, `jj workspace list` in the project reports at least two workspaces with the anchored working copy among their targets and the new directory's own `@` among them, and a plain `jj status` — deliberately without `--ignore-working-copy` — succeeds there. The resolve-from-inside check is what closed the measured `jj git init` cheat that had scored 1.0.

`3 tests, 0 floored · anchored · provisional, held for coverage`

**Known hole.** With no anchor file the identity claim degrades to 'the project's current `@` resolves inside the workspace', and one assertion compares `jj workspace root` stdout against a hardcoded path literal.

## Proposed — 9 designs, none built

Nine designs, none of them built: no fixture exists, no verifier exists, nothing has been run or measured. The 'graded' sentences describe what a verifier would assert, not what one does. The tenth slot is unassigned — N10 was struck because requiring an interactive route is a method constraint and an R3 violation, and the proposal's own answer is to fill the slot from the survey's Tier 3 (2.1 split-by-path or 3.3 absorb-into-a-stack cover the salvageable ask, which is 'move exactly one hunk and leave the rest of the commit alone'). Until someone chooses, the target set is 23 tasks and one empty slot. Two rules were applied to every prompt: state every constraint the verifier scores and nothing it does not, and never name the technique, the subcommand or the flag.

### N1 — a conflict that propagates instead of being resolved on the spot

```text
The rebase of retry-backoff onto main left src/client/retry.py conflicted in 'make the retry budget configurable', and everything above it is carrying the conflict too. Fix it in that commit — keep main's renamed REQUEST_TIMEOUT and my RETRY_BUDGET setting — and leave the stack as the four commits it is now, each with the changes it has.
```

**Setup:** retry-backoff's four commits have already been rebased onto a main that moved underneath them; the second of the four conflicts in src/client/retry.py because main renamed TIMEOUT in the same lines that commit added RETRY_BUDGET, and the two commits above it and the empty working copy all carry the propagated conflict. **Graded:** `conflicts()` empty across the whole repo, the four anchored change ids still resolving in the same order each carrying its own diff, no fifth commit between the anchored middle change and the anchored head, and retry.py at the head matching the single satisfying content line-wise. It discriminates the git-shaped model in which a conflict halts work and must be cleared before anything else happens — unpicking the stack commit by commit and landing a fixup on top both leave the anchored middle change conflicted.

`design stage, nothing built · wording drafted`

**Open question.** Naming REQUEST_TIMEOUT and RETRY_BUDGET pins the resolution so it can be graded, but it tells the agent what the conflict contains before it looks.

### N2 — a merge commit the agent creates

```text
I need rate-limit and oauth-refresh brought together: make a commit that sits on top of both, with config.toml carrying the [ratelimit] block from one and the [oauth] block from the other. Don't rewrite the commits on either bookmark.
```

**Setup:** rate-limit and oauth-refresh diverge from main, their tips edit the same region of config.toml so they conflict textually, and there is no merge anywhere in the repo. **Graded:** `@` has exactly two parents whose change ids are exactly the two anchored tips, the merge renders `conflict == false`, config.toml holds both named blocks at the one satisfying content, and both tips still resolve to their bootstrap commit ids — unchanged commit ids, not merely surviving change ids, which is what kills the hand-written single-parent union. It discriminates hunting for a `jj merge` subcommand from knowing that a commit can simply have two parents.

`design stage, nothing built · wording drafted`

**Open question.** That there is no `jj merge` subcommand is marked 0.38-only in the provenance roster and has to be re-probed on 0.44 before authoring, since the whole discrimination assumes it.

### N3 — recovering from a mistake buried in the operation log

```text
I squashed 'return 409 on duplicate keys' into 'add idempotency key to charge requests' by mistake, and I've made two more commits since then. Get those back to being two separate commits exactly as they were, without losing the work I did afterwards.
```

**Setup:** two commits above main that should have stayed apart, which the bootstrap has already squashed together, plus two further commits of real work made afterwards so the mistake is neither the first nor the last entry in the operation log. **Graded:** both anchored change ids visible again as separate commits in their original order, each carrying its own diff; the two later anchored changes still resolving with their bootstrap commit ids intact; an `--at-op` replay confirming the recovered commits are the originals rather than reconstructions; and every divergence addressed through `change_id(X)` rather than a bare change-id revset or the literal X/0, X/1 offsets. It discriminates undoing the most recent operation (which reverses the changelog commit) and rewinding to a pre-mistake operation (which reaches a repository missing the later work) from reversing one operation out of the middle of the history.

`design stage, nothing built · wording drafted`

**Open question.** The correct route leaves a residual divergent change and legitimately drops a change id, so this will need an `anchor_exemptions.json` — and a green pre-sweep cannot reveal that it is missing, because the untouched image never does the work that breaks the assertion.

#### What this task sets up, and what it evaluates

**The setup.** The agent is handed a repository with a mistake already baked into it and some work done on top of the mistake. On top of main there were two commits — one adding an idempotency key to charge requests, one returning 409 when a duplicate key shows up — and the bootstrap squashed the second into the first, so the repository now holds a single commit carrying both changes and the second commit's message is gone. The bootstrap then made two more commits, a retry-budget change and a changelog entry, so the mistake sits three operations back rather than being the last thing that happened.

**A correct recovery** ends with those two commits separate again, carrying the same identities they had before the squash, and with the two later commits still present and unmodified.

**The obvious moves each fail in their own way.** Undoing the most recent operation reverses the changelog commit instead of the squash. Rewinding the repository to the state it was in before the squash also erases the two later commits, because that is time travel rather than an inverse patch. Hand-splitting the combined commit back into two produces commits that look right in a log but are new ones, which the verifier can tell apart from the originals.

**What is being evaluated** is whether the agent knows that jj's record of past operations lets you reverse one specific operation out of the middle of the history without disturbing what came after it — and, just as importantly, whether it can tell that apart from rewinding to an earlier point in time.

**Why it earns a slot.** This is precisely where the model most people carry over from git breaks: git's reflog lets you go back to a state, and an agent reasoning by analogy will reach for the equivalent here and quietly destroy a day of work. The cost is invisible from the end state — the repository looks perfectly fine, it just has less in it — which is exactly why it has to be graded rather than eyeballed.

### N4 — revsets the agent writes

```text
get the change ids of all the tips not yet part of main and put them in unmerged.txt, each id on its own line
```

**Setup:** roughly sixteen commits across six lines of work — main, two already-landed bookmarks whose tips are ancestors of main, and four heads that are not — deliberately large and interleaved enough that reading the log and transcribing tips by eye is not a viable route. **Graded:** the reference revset is evaluated in the repo at verification time and unmerged.txt must equal that set of change ids exactly, so the expected answer never appears as a constant; every read passes `--ignore-working-copy` so the verifier does not snapshot what it is grading, and anchored ids confirm the history was not restructured to make a wrong answer true. Whether the agent composed a revset or worked it out by hand is not graded.

`design stage, nothing built · Hugh's wording, verbatim`

**Open question.** An answer-file task invites a zero-tool-call guess, so some fraction of trials measures agency rather than jj skill; the proposal prefers a form where the revset is the route to an action rather than the deliverable.

### N5 — filesets

```text
roll back the src/ changes but don't change the generated tree
```

**Setup:** one commit, 'wire up the new charge client', touching both hand-written code under src/ and a regenerated tree nested under src/generated/, whose files carry machine-looking content with a recorded hash so they cannot be plausibly reconstructed — over-restoring and then re-adding them fails byte-equality. **Graded:** the anchored change's changed paths are exactly the generated set and nothing else, every file under src/generated/ matches the bootstrap byte for byte, and the change id survives the rewrite while the commit id changes, which is what distinguishes an in-place rewrite from a rebuilt commit. Doing it file by file also passes — the fileset is the cheap route, not the graded one. It discriminates a whole-directory restore, which silently takes the nested generated subtree with it.

`design stage, nothing built · Hugh's wording, verbatim`

**Open question.** No survey theme backs this one, so standing the fixture up and solving it on the pinned binary is the first authoring action rather than a later check.

### N6 — immutability

```text
jj is refusing to reword anything in my stack — it says the commits are immutable — and 'fix nonce handling' should say 'fix nonce handling on retried charges'. Sort it out so I can rewrite my own commits again, and keep main and everything below it protected from rewrites.
```

**Recast.** Recast to a single functional ask after the 'two unrelated tasks' objection: the standalone 'set the repo up so nothing can be rewritten' errand is gone, and the agent now enters on a refusal it has to diagnose. That is also the defence against the risk in the original — a prompt that opens by asking for protection reads like branch protection and pulls toward git-side mechanisms (hooks, `receive.denyNonFastForwards`, read-only files) that jj never reads.

**Setup:** main with two commits below it and a four-commit stack above, and an over-wide immutability alias the bootstrap has already configured through `jj config set --repo`, so the user's own stack is protected along with main and every rewrite in it is refused. **Graded:** the configured alias is evaluated in the repo and never string-matched — the anchored main change must still be inside it and the anchored stack commits must not — the anchored 'fix nonce handling' change carries the corrected description under the same change id with a new commit id, and the anchored commit below main is byte-identical to the bootstrap's. Both halves are scored, so narrowing the protection without doing the reword, and rewording while leaving main unprotected, each fail.

`design stage, nothing built · wording drafted`

**Open question.** jj 0.44 silently accepts five config keys it removed — they exit 0, print nothing, list back happily and do nothing — so an agent that writes a plausible key sees no error and reports done. That is why the alias must be evaluated rather than read.

### N7 — the operation log as something you diagnose

```text
Before I re-run the tests I need to know which commits actually changed when I rebased retry-backoff onto main — put their change ids in touched.txt, one per line.
```

**Setup:** an operation log holding one multi-commit rebase — retry-backoff's four commits moved onto an advanced main — among several small operations made afterwards, so the rebase is not the most recent entry and has to be found. **Graded:** the operation's effect is recomputed at verification time by `--at-op` differencing, reading the repo at the operation and at its predecessor and taking the change-id delta, and touched.txt is compared as a set; the expected set is never a constant, so a guessed list of plausible ids cannot match. It discriminates guessing the touched set from `jj log`, which shows the current graph rather than what the operation changed.

`design stage, nothing built · wording drafted`

**Open question.** `--no-integrate-operation` and `jj op integrate` are real on 0.44, so an agent can produce side effects that leave no operation-log entry — which means a verifier reconstructing truth by `--at-op` differencing is reasoning over a log no longer guaranteed complete. The proposal wants this probed before N7 is authored.

### N8 — divergence as a thing to work with

```text
jj is showing 'add idempotency key to charge requests' twice and the idempotency bookmark is in a conflicted state. Keep the copy that has tests/test_charge.py in it, get rid of the other, and leave idempotency pointing at the one that survives.
```
