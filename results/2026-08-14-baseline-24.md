# 2026-08-14 baseline, 24 tasks, informed arm

First baseline against the current 24-task suite, with the agent told it is in a jj
repository. **The run did not finish.** It was designed as 552 trials — haiku and sonnet at 10
attempts, opus at 3 — and reached 326 before the container ran out of disk. The opus 72 were a
separate invocation that never launched, so this job's `config.json` records only the 480.
There is no opus arm at all, and haiku and sonnet have 5–7 scored attempts per task, not 10 —
read every number below against the per-task denominators.

**What was run.** 24 tasks, `claude-code` adapter (CLI 2.1.232), harbor 0.20.0, docker, jj
**0.44.0** in every image, 21:17:37Z–22:16:33Z, **59 minutes** at `-n 8`. The images were built
from **`repro/2026-08-14-informed-arm-images` @ `42273ba1ac`** — `main` @ `9dc4ac6ae9` plus
exactly one commit on top, which touches only the 24 task Dockerfiles (24 files, +312, nothing
outside `tasks/`) and adds the `AGENTS.md` layer described below. **Do not pin `9dc4ac6ae9`
for this arm.** Earlier drafts did, and that pin is wrong in the one way that matters: there is
no `AGENTS.md` or `CLAUDE.md` anywhere in that tree, so a reader who checks it out and re-runs
gets **the control arm** — the other side of the experiment. No measurement here moves, because
the diff is Dockerfile-only and every verifier, floor and test is byte-identical between the two
trees; the defect was entirely one of reproducibility. That branch is pushed **for reproduction
only** — <https://github.com/moredatarequired/jj-benchmark/tree/42273ba1ac>, the commit rather
than the branch tree, so the link cannot drift if the branch moves — and has no PR: whether the
informed arm ships as a change to the suite is a separate and still-open decision.

Scores come from each trial's `verifier_result.rewards.reward`; a trial with no
`verifier/ctrf.json` is ERRORED-INFRA and is excluded, never scored 0. There are **327 trial
directories but 326 trials** — `git_fetch_remote__mx2TCa5` is a stub with no `result.json`, no
`exception.txt` and no `ctrf.json`, so it is neither scored nor ERRORED-INFRA; count
directories rather than results and you get 54 errored and haiku 26. The repository's own
`scripts/check_run_results.py` reports 53, agreeing with this file: it finds trials by
`result.json` or a `verifier/` directory, the stub has neither, so the tool never discovers it
at all rather than classifying it.

## The informed arm

Every task image carries `/home/user/AGENTS.md` with `/home/user/CLAUDE.md` symlinked to it:

> This project uses Jujutsu (`jj`) for version control. Please use `jj` for all
> version control work in this repository; `git` should not be used for it.

Nothing task-specific. It sits one directory **above** the project, never inside the fixture
repo: a committed copy was measured to cap `abandon_commits` at 0.750 and `operation_recovery`
at 0.800, both verifiers asserting an exact tracked-file set. Both caps are `(scored−1)/scored`
with `scored = tests − floor` off `vacuity_floor.json`, 4−0 and 8−3; an earlier note said
0.875, dividing by 8 rather than 5. Delivery was verified two ways before any spend. What is
load-bearing is the **filename** `CLAUDE.md`, not the symlink: a prompt capture inside the
built image shows `/home/user/CLAUDE.md` delivered under `Contents of /home/user/CLAUDE.md
(project instructions, checked into the codebase):`, a bare `AGENTS.md` is delivered nowhere —
neither at the parent position nor at the project root — and a relative symlink, an absolute
symlink and a plain copy all deliver identically. Measured on Claude Code 2.1.235 in the task
image and reproduced on 2.1.42 against a replica of the layout; an earlier note here said the
symlink was load-bearing, which is withdrawn. (There is no PR for this arm to carry the
method — an earlier draft pointed at one.)

**The arm took.** Of 273 scored trials, **261 (95.6%) ran `jj` at least once** — haiku 126/138,
sonnet 135/135. Both comparators come from the one-trial-per-cell A/B earlier the same day, 48
trials per arm: uninformed control **12/48 (25%)**, haiku 0/24, `main` @ `c6eeee9541`, job
`2026-08-14__18-06-02`; in-fixture informed arm **45/48 (94%)**, `claude/agents-md-arm` @
`c9851c8727`, job `2026-08-14__18-48-23`. **That second pin resolves for nobody:** the branch
was never pushed, so `c9851c8727` exists only in the local checkout it was measured in and that
arm is not reproducible here. Earlier drafts flagged that while quietly carrying the identical
defect in this sweep's own pin; that one is now fixed at the top of this file, and the two are
held to one standard — a pin that names a tree nobody can fetch is not a pin. The control's
`c6eeee9541` does resolve, on `main`. Neither comparator was re-run at depth — one draw per cell
against this sweep's five to seven, so the direction is solid, the magnitudes coarse.

## Ceiling, floor, discrimination

**At ceiling on both models (5):** `fileset_rollback`, `squash_range`, `undo_mistaken_rebase`,
`workspace_add`, `workspace_update_stale`. They contribute nothing to **detecting an
improvement** — but a task at ceiling has no room up and *full* room down, which makes these
five the suite's only regression detectors, concretely so right after the 0.38 → 0.44 re-pin.

**At floor on both models (1):** `operation_recovery` — **0/12 at n=6 per model**, no partial
credit, ten of twelve anchor-zeroed. The two trials that did not trip the anchor passed exactly
the three vacuity-floor tests and failed all five scored ones, so nothing here shows it being
solved; but those two are the only trials that could inform the question, and **n=2 is not a
basis for calling a task unsolvable.**

`template_customize_log_output` is next to it at 0.000 / 0.200, but **not** for the
`jj config set` grader artifact this file previously named — #24 fixed that before the sweep
commit, and at `9dc4ac6ae9` the verifier compares *rendered* output. Off the trial records the
11 scored trials are:

* **4 wrote a template *function* alias** (key `template-aliases.'log_custom()'`), **all four
  sonnet**. Under `jj log -T 'log_custom()' --no-graph` it renders **byte-identically to the
  verifier's own reference template**. But the verifier looks up the bare keyword, so
  `jj config get template-aliases.log_custom` finds nothing and `jj log -T log_custom` dies
  with ``Keyword `log_custom` doesn't exist``: both scored tests fail (`tests` 2, `floor` 0),
  so a working answer scores exactly **0**, no partial credit.
* **1 sonnet trial passed** (`__ihz3TDo`) — keyword form on the first and only attempt,
  trailing `++ "\n"` present. **Sonnet's 0.200 is that trial;** the alias-form defect is the
  0.800 shortfall, not the 0.200.
* **6 haiku misses — all six haiku trials, not five.** Five omit the trailing `++ "\n"`, one
  (`__McnwCaW`) omits the `++` operators entirely, and all six name `change_id.short()` — so
  "or never naming `change_id.short()`" is withdrawn. `__X4C7y7m` was bucketed with the
  function-form trials on its verifier stdout, but it is **haiku**: it wrote a *keyword* alias
  to `/home/user/.config/jj/config.toml`, a path jj never reads since agent and verifier both
  run as root with `HOME=/root`, with a body jj cannot parse
  (`description.lines().next().unwrap_or("")`) — and never ran jj at all.

**A verifier rejecting a correct solve, not a matter of taste.** The instruction asks for "a
template alias called `log_custom`" without saying which of jj's two alias forms; one of them
does exactly what is asked and scores zero. The form is a **free naming choice, made before any
feedback**: all four function-form trials keyed the alias `log_custom()` up front, with nothing
in the task text or in any tool output pointing either way. Three of them later ran the bare
keyword and read ``Keyword `log_custom` doesn't exist`` — but in all three that error arrived
*after* the key was already written, so it is a consequence of the choice rather than
information about it, and it says nothing about whether the keyword form would have worked.
Earlier drafts of this file put it both ways and both are wrong: this is not "a choice made
with full information", and it is not something "the grader decides and the model does not".
The model picks the form unprompted, and then ships it — closing by telling the user to invoke
`log_custom()`, so the choice is at least user-visible. The trailing newline is easy to miss
for a related reason: under jj's **default graph view** an alias missing `++ "\n"` is
indistinguishable from a correct one, because the
graph renderer supplies the break (`__7wbuGkJ` shows both renderings of one broken alias), and
the task's own truth plan checks with the graph command. Only `--no-graph` exposes it.

**18 of 24 separate the two models**, the largest gap `mistaken_squash_recovery` (+1.000) and
the smallest `rebase_branch` (+0.100). **Sonnet is at 1.000 on 20 of 24; haiku on 5** — at
n=5–7, where one trial moves a task mean 0.143–0.200 (of the 48 cells, 16 are n=5, 31 are n=6,
and one is n=7 — `absorb_changes` haiku, the 0.143), so read that as coarse, and the same
caveat governs what follows. Of the four tasks off ceiling for sonnet, `operation_recovery`
cannot carry an A/B: 0/12, no partial credit, ten of twelve anchor-zeroed — no room down, no
gradient up. `template_customize_log_output` is **not** disqualified; that earlier conclusion is
withdrawn. Sonnet is **1 of 5** on it — `__ihz3TDo` wrote the keyword form first try and scored
1 — so the task is off ceiling with real spread and **stays in the A/B set**. Weight it
carefully rather than at face value: the spread is a free form choice rather than jj
capability, and the grader rejects one correct form outright, so a number quoted off it
measures naming as much as skill. **A sonnet improvement A/B therefore rests on
`absorb_changes` (0.889), `git_fetch_remote` (0.917) and one task with a known-broken grader**
— not enough for anything short of a very large effect at these N. A **regression** A/B is in much better shape: the
twenty tasks at 1.000 have full room down and carry one at full power. For improvement, fix the
grader and re-measure, or run on haiku, where 19 tasks are off ceiling.

## Anchor audit

All three pre-flight steps ran clean with `--keep-images` on the sweep's daemon: `--write`
measured 24/24 anchorable, `--check` matched a fresh measurement, and `--verify-untouched`
confirmed reward 0, a written `ctrf.json` and a holding anchor on every task.

What the third does and does not establish about the **exemptions** is worth being exact about.
It *does* prove they are **not stale under 0.44**: `bootstrap_anchor.py`'s own contract is that
it asserts the anchor HOLDS rather than merely not-failing, and an exemption entry that no
longer resolves makes `tests/anchor.py` abstain — so a clean pre-flight means all three
`operation_recovery` exemption entries still resolve against these images. What it *cannot*
exercise is the **suppression** path — `violations()` consulting `may_disappear` /
`may_be_divergent` — because it runs against the **untouched** bootstrap, where nothing is
missing or divergent and so nothing needs suppressing. So: the exemptions are not stale under
0.44; there is **no evidence that they correctly suppress a real violation.** (An earlier draft
of this file said "zero evidence about exemption correctness", which over-corrected.)

**27 of 273 scored trials carry `BOOTSTRAP_ANCHOR_VIOLATION`** — the denominator is 273, not
326: all 27 have a `verifier/ctrf.json`, and the 53 ERRORED-INFRA trials never reached a
verdict, so they can carry neither a violation nor a reward. The codes are 23
`ANCHOR-CHANGE-ID-MISSING`, 4 `ANCHOR-CHANGE-ID-DIVERGENT`, 1 `ANCHOR-HANDOVER-OP-GONE` — 28
across 27 trials, because `restore_interactive__932AiA5` carries both of the first two. By
task: `operation_recovery` 10, `split_commit_interactive` 4, `mistaken_squash_recovery` 3,
`propagated_conflict` 3, `immutable_stack` 2, `restore_interactive` 2, one each on
`divergent_change`, `edit_commit_message`, `track_untracked_file`. **By model: 22 haiku, 5
sonnet**, the five sonnet all on `operation_recovery`.

**Read: true positives where they were read** — 12 of the 27, and this says which.

*Read individually (2).* The `ANCHOR-HANDOVER-OP-GONE` agent ran `rm -rf .../.jj && jj git
init`, after trying `git update-ref -d` and `git gc --prune=now` inside `.jj/repo`. On
`propagated_conflict` an agent ran `jj abandon @` then `jj new <changeid> -m "<the original
description>"`, fabricating a same-description replacement.

*Read as a cluster (10).* On `operation_recovery` the ten are all agents reaching for
`jj abandon` on Commits 3/4/5 instead of `jj op restore`; all ten trajectories contain a
`jj abandon` call and none runs `jj op restore`, so that is a check over the whole cluster and
not a sample. The exemption file deliberately does **not** exempt Commit 3, because Requirement
4 asks for the specific empty commit that later became it — and the two trials that went
another route failed that same requirement on the merits.

*Not read (15).* Counted, not inspected; nothing here claims they are true positives. An
earlier draft called the four `DIVERGENT` cases duplicated rather than rewritten commits; no
`jj duplicate` appears in any of the four trajectories, so that is withdrawn.

No `ANCHOR-HANDOVER-OP-GONE` accompanied any `ANCHOR-CHANGE-ID-MISSING`. No trial ran against a
cold-rebuilt image — but that is established by the stronger fact below, that a cold `docker
build` cannot succeed here at all, not by this code pattern. The pattern is a separate fact
about jj: 0.44 persists change ids in a `change-id` header on the git commit object, so a
`.jj`-only wipe plus `jj git init` re-imports them byte-identically — invisible to the
change-id check, caught by the handover check.

## Why it died

The full postmortem belongs in a sweep-procedure doc; two numbers matter here. **Usable disk is
about 40 GB, not the 252 GB `df` reports**; the sweep launched with 13 GB free, and **harbor
rebuilds the task image per trial** (`pull_policy: build`, `delete: true`), so BuildKit cache
consumed that 13 GB over 326 trials — about **40 MB per trial**, meaning a 480-trial sweep needs
roughly **19 GB of headroom at launch**. (An earlier 33 MB/trial figure gives 16 GB and does not
reproduce the death at 326; provision from 19.) And **a cold `docker build` cannot succeed in
this container at all** — the pip layer dies with `CERTIFICATE_VERIFY_FAILED` against the agent
proxy's re-terminated chain — so `docker system prune -a` destroys the ability to build rather
than recovering space.

**The 53 ERRORED-INFRA trials are all at the end** — the first starts at 22:09:27Z, every trial
before it has a verdict, and they hold start-order positions **266–326 of 326** (1-indexed;
265–325 zero-indexed, which an earlier draft mixed with the 1-indexed total). They are
`NonZeroAgentExitCodeError` (28), `NetworkConnectionError` (21), `CancelledError` (4); zero
retries fired before that point. **Excluding them is not shown to be neutral.** The only
sensitivity check this data supports measures the *included* trials — eight scored trials
started after 22:09:27Z, and dropping them moves haiku's mean by 0.0000 and sonnet's by 0.0019
— which is silent about the 53 that were dropped. Nor are those 53 spread evenly across the
per-task table: counts run 1 to 4 (`duplicate_range`, `track_untracked_file`,
`workspace_update_stale` at 4; `absorb_changes`, `bookmark_left_behind`, `git_fetch_remote`,
`template_customize_log_output` at 1), so per-task denominators are unevenly thinned. And
calling them the shapes a container takes when the filesystem is full rather than agent
behaviour infers mechanism from timing: 28 of the 53 are `NonZeroAgentExitCodeError`, which on
its face names the agent, and no container was opened to check. On direction: the censoring is
concentrated in the tail of the schedule rather than selected on difficulty — not a clean
suffix, since the eight scored trials noted above interleave among the 53 — and per-task error
count correlates weakly and *positively* with haiku's per-task mean (r = +0.28, 24 tasks), so
the obvious worry — hard trials cut, means flattered — is not what this shows. Neither
neutrality nor bias is demonstrated.

## Read this before quoting any number

**N is 5–7 per task per model, and the design was 10.** Any variance or power estimate off this
data is computed on uneven, small N; at n=6 a task's mean moves 0.167 per trial, so a one-trial
difference is not a signal. This governs the saturation reading and the A/B recommendation
above, not only this section.

**No prior sweep number is comparable.** The 2026-08-12 baseline measured 53 tasks; 39 were
deleted and ten authored since, and several survivors have had their verifiers rewritten. The
bootstrap anchor did not exist then — but the **vacuity floor did**, at `68525335e6`, scoring
that very sweep, so floor correction is not one of the differences.

**This is the informed arm, so it is not a control.** It licenses no statement about the
uninformed case beyond the jj-usage counts above. And a 6/6 is a ceiling, not proof of
determinism — "no failure observed in six draws" and nothing stronger.

**An anchor violation scores 0 and is indistinguishable from a task failure in the aggregate.**
The 27 above are inside the per-task means; on `operation_recovery` that is most of the row,
and the per-model split moves the headline gap by 0.079 (0.317042 → 0.238484).

**jj is pinned at 0.44.0** in every image, but the anchor exemptions were reasoned against jj
0.38.0 behaviour and re-validated here only by `--verify-untouched` — which establishes that
they still resolve, and nothing about whether they suppress a real violation correctly.

**Cost is understated relative to a finished run:** $39.53 harbor / $31.24 corrected bought 326
trials, not 552, and no opus.

so you can weigh them accordingly:
